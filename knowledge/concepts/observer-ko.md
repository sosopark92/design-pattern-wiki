# 옵저버 (Observer)

옵저버 패턴은 구독 메커니즘을 정의하여 관찰 대상인 객체에서 발생하는 모든 이벤트에 대해 여러 객체에게 알림을 보낼 수 있도록 하는 행동 디자인 패턴입니다. 여러 옵저버 객체가 주제(Subject)를 감시하고 주제의 상태가 변경될 때 모든 옵저버가 자동으로 알림을 받는 일대다 관계를 구성합니다.

## 의도

옵저버 패턴의 의도는 다음과 같습니다:

- 한 객체의 상태가 변경될 때 모든 종속 객체가 자동으로 알림을 받도록 일대다 종속성 정의
- 주제(주관자)와 옵저버를 분리하여 낮은 결합도 유지
- 런타임에 옵저버의 동적 구독/구독 해제 허용

## 문제점

객체가 다른 객체들에게 상태 변화를 알려야 할 때, 모든 옵저버에 대해 강한 결합도를 유지해야 합니다. 새로운 옵저버를 추가하려면 주제 클래스를 수정해야 합니다. 주제가 옵저버에 직접 참조를 유지하므로 구독 해제가 어려워집니다. 옵저버들이 서로 다른 알림 요구사항을 가질 때, 주제는 모든 변형을 알아야 합니다.

## 해결방법

옵저버 패턴은 옵저버가 주제에 자신을 등록하는 구독 메커니즘을 도입합니다. 주제의 상태가 변경될 때, 등록된 모든 옵저버를 순회하며 각각의 알림 메서드를 호출합니다. 옵저버는 동적으로 구독 및 구독 해제할 수 있습니다. 주제는 구체적인 옵저버 타입을 알 필요가 없고, 옵저버 인터페이스를 구현한다는 것만 알면 됩니다.

## 구조

네 가지 핵심 참여자:

1. **주제 (Subject)** — 옵저버 목록을 유지하고 추가/제거 메서드 제공; 상태 변경 시 모든 옵저버에 알림
2. **옵저버 (Observer)** — 주제 변경에 대해 알림을 받아야 하는 객체들의 인터페이스 정의
3. **구체적 주제 (Concrete Subject)** — 상태 저장 및 옵저버에 알림 전송
4. **구체적 옵저버 (Concrete Observer)** — 주제에 대한 참조 저장 및 옵저버 인터페이스 구현; 주제로부터 업데이트 수신

## 사용 시기

- 한 객체의 변화가 다른 객체들의 변화를 요구하고, 영향 받는 객체의 수가 미리 알려지지 않은 경우
- 객체가 다른 객체들에게 알려야 하지만, 그 객체들이 무엇인지 가정하고 싶지 않은 경우
- 느슨한 결합 아키텍처를 원하며 객체들이 간접적으로 통신하길 원하는 경우
- 런타임에 옵저버의 동적 구독/구독 해제가 필요한 경우

## 사용하지 말아야 할 경우

- 옵저버 개수가 컴파일 타임에 고정되고 알려진 경우 (직접 메서드 호출이 더 간단할 수 있음)
- 즉시 알림이 보장되어야 하는 경우 (옵저버는 비동기로 통지되므로 지연 발생)
- 옵저버 콜백이 특정 순서를 요구하는 부작용을 가진 경우 (알림 순서가 예측 불가능)
- 성능이 중요하고 옵저버 알림 오버헤드가 받아들일 수 없는 경우

## 실제 사용 예시

- GUI 프레임워크의 이벤트 리스너 (버튼이 클릭 핸들러에게 알림)
- Pub-Sub 메시징 시스템 (메시지 브로커가 구독자에게 알림)
- MVC 프레임워크 (모델이 뷰 변경에 대해 알림)
- 분산 시스템의 실시간 이벤트 버스 ([[knowledge/reviews/opencode-bus-ko]] — 타입별 및 와일드카드 이벤트 구독)

## 장단점

### 장점

- 개방-폐쇄 원칙 — 주제를 변경하지 않고 새로운 옵저버 추가 가능
- 느슨한 결합 — 주제와 옵저버가 서로에 대해 세부 사항을 알 필요 없음
- 동적 구독 — 런타임에 옵저버 추가/제거 가능
- 런타임 유연성 — 주제가 구체적인 옵저버 타입을 알 필요 없음

### 단점

- 옵저버 알림 순서가 예측 불가능
- 옵저버를 제대로 구독 해제하지 않으면 메모리 누수 발생 가능
- 많은 옵저버가 있을 경우 성능 오버헤드
- 알림 순서와 옵저버 간 종속성을 추적하기 어려움
