# Daily Log: 2026-04-19

## Session (14:00) - Opencode Bus: Event Bus as Observer variant

**Source analyzed:** raw/snippets/opencode/src-bus-index.ts

**Key observations:**

- `Bus.Interface` (lines 31-43) is the classic Observer Subject interface — `publish()` = notify, `subscribe/subscribeCallback()` = register
- **Two-tier dispatch** (lines 26-29, 86-107): State holds a `wildcard` PubSub and a `typed` Map<string, PubSub>. On `publish()`, the event goes to the typed channel (if it exists) AND the wildcard channel. This means: type-specific subscribers get a dedicated channel; wildcard subscribers pay no extra cost per event type.
- `getOrCreate()` (lines 74-83): typed channels are created lazily — no PubSub is allocated until someone subscribes to that type. Smart memory optimization.
- **Push vs Pull Observer variants** both appear here:
  - Pull: `subscribe()` returns a `Stream<Payload>` — consumer drives consumption
  - Push: `subscribeCallback()` calls a callback when event arrives — bus drives delivery
- `on()` (lines 130-155): Scope-based cleanup. Returns `() => void` — the Disposable pattern. Subscriber forgets to call it → resource leak.
- `GlobalBus.emit()` (line 100): bridges the local bus to a global external bus. The local bus is the Subject; GlobalBus is a second Observer of everything.

**Patterns identified:**

- **Observer** — core mechanism, implemented via Effect's `PubSub`
- **Event Bus** — higher-level abstraction over Observer; Subject becomes a shared intermediary, producers never hold observer lists
- **Registry** — `BusEvent.define()` registers event types with Zod schemas; seen in `BusEvent` namespace
- **Two-tier Dispatch** — performance optimization splitting wildcard vs typed channels
- **Disposable/Scope** — `on()` returns cleanup function; Effect `Scope.make()` manages lifecycle

**Key insight — how Event Bus differs from basic Observer:**

In basic Observer, producers (Subjects) hold their own observer lists. If `UserService` and `OrderService` both emit events, each maintains its own subscriber list — coupling emerges when consumers need events from multiple subjects.

Event Bus moves the observer list into a shared intermediary (the Bus). Producers just call `publish()` — they never know who's listening. This is Observer where the Subject role is extracted into a reusable singleton. The tradeoff: all events share one channel, so event type management (Registry) becomes necessary.

**Lessons learned:**

- Two-tier dispatch solves the "wildcard tax" problem: without it, a wildcard subscriber forces every publish to fan-out to every subscriber, even for irrelevant types
- Lazy channel creation (`getOrCreate`) is important — pre-allocating a PubSub per event type at startup wastes memory if most types are never subscribed to
- Effect's `PubSub` + `Stream` give the bus async backpressure for free — something callback-based buses must implement manually
- The `on()` function's scope pattern is the correct way to handle subscription cleanup; bare callback arrays (common in naive implementations) leak
